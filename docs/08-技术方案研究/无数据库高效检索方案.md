# 古籍通｜无数据库方案：5GB超大TXT古籍文件 高效稳定检索最优实现方案

**核心结论（定稿）**：完全**不需要数据库**。5GB纯文本最优生产方案为：**本地离线分词分块 + 静态倒排索引文件 + 前端内存检索 + 文本分片懒加载**。体积可控、检索毫秒级、Vercel 零报错、无膨胀、无服务端压力。

## 一、为什么「不用数据库」反而更适合本项目5GB文本？

针对古籍静态只读场景，数据库属于**多余且拖垮性能的中间层**：

- 古籍文本**只读、不增删、不修改**，无需事务、无需动态写入
- 入库必然体积膨胀（5GB→10GB+），索引后可达15GB+
- 服务端检索有超时、OOM、连接开销，静态站完全用不上
- Vercel/静态部署环境不适合重型数据库常驻

**无数据库架构优势**：零服务端压力、零体积膨胀、零部署故障、检索速度远超数据库模糊查询。

## 二、无数据库核心架构：纯静态文件检索体系

整体架构：**原始GitHub TXT源文件 + 本地预构建静态索引池 + 前端内存检索引擎 + 分片懒加载阅读**

全程无数据库、无后端接口、无持久化存储，纯文件驱动。

### 2.1 第一步：文本分块（解决超大文件卡死问题）

对5GB整本TXT执行**固定粒度智能分块**，不破坏语义、不割裂章节：

- 单块大小：**2KB–4KB/块**（古籍文本最优粒度）
- 按章节、卷次、段落自动切分，优先语义截断
- 每一块生成唯一ID、归属书籍、归属馆藏、偏移位置

### 2.2 第二步：构建「轻量静态倒排索引」（无数据库检索核心）

离线脚本遍历全量5GB文本，生成**JSON/NDX 静态索引文件**，替代数据库全文索引。

索引文件仅存储检索关键数据，**不存原文**，极致瘦身：

- 字词词条（去重、归一化、适配古文字）
- 词条对应块ID、书籍ID、章节位置
- 词频权重、匹配类型（标题/章节/正文）
- 原文远程Raw地址、片段偏移量

**索引最终体积：300MB–700MB**

### 2.3 第三步：索引分片打包（适配前端加载）

不使用单一大索引文件，采用**按馆藏分类拆分索引**：

- ru.json（儒藏）、yi.json（医藏）、shi.json（史藏）……十大分类独立索引
- 用户检索时**按需加载对应分类索引**，不一次性加载全量索引

### 2.4 第四步：前端内存检索引擎（毫秒级响应）

Next.js 前端基于轻量化检索库实现纯客户端检索：

1. 用户输入关键词
2. 自动匹配对应馆藏索引文件、懒加载至内存
3. 前端完成词条匹配、权重排序、高亮匹配
4. 返回结果：书籍名、章节名、文本片段、定位地址

**检索响应速度：20–80ms**

## 三、检索结果权重排序规则

内置静态权重规则，无需数据库排序函数：

标题完全匹配 > 章节名匹配 > 段落开头匹配 > 正文普通匹配 > 词频高优先

## 四、原文加载机制（解决GitHub大文件无法读取问题）

- 索引记录每一段文本在GitHub Raw的字节偏移
- 用户打开章节时，通过 Range 请求**只拉取对应片段**
- 不拉取整本大文件，规避GitHub超时、截断、限流问题
- 前端缓存已读片段，二次打开零加载

## 五、繁简双语检索兼容方案

离线预构建**繁简双向映射索引**：

- 索引同时收录繁体原词、简体对照词
- 用户简体输入可匹配繁体原文，繁体输入可精准溯源古字
- 无需运行时转换、无错转、无异体字丢失

## 六、版本迭代与更新机制

- 上游GitHub古籍资源更新：本地重新执行分块+索引脚本
- 更新静态索引文件，直接提交仓库部署
- 线上服务零停机、零重构、无数据迁移成本

## 七、方案对比：无数据库 VS 数据库方案

| 对比项 | 数据库方案（不推荐） | 纯静态索引方案（最终方案） |
|-|-|-|
| 文件体积 | 5GB→10GB~20GB（严重膨胀） | 原5GB不变+索引300-700MB（无膨胀） |
| 检索速度 | 服务端查询，数百ms~数s | 前端内存检索，20~80ms |
| 部署难度 | 高，需数据库部署、迁移、维护 | 极低，纯静态文件，Vercel一键部署 |
| 限流/崩溃风险 | 高，大文本查询极易超时OOM | 零风险，无服务端计算压力 |
| 古字/繁简适配 | 通用库转换易出错 | 离线预映射，保真零错 |
| 长期维护成本 | 高（备份、迁移、优化） | 极低（仅更新索引文件） |

## 八、已写入PRD的无数据库硬性技术规范

1. 本项目**全程不使用任何数据库**（MySQL、SQLite、MongoDB等全部舍弃），采用纯静态文件索引架构
2. 所有检索能力基于**本地离线分块+静态倒排索引**实现，线上无动态计算
3. 索引按十大藏库分类拆分，按需懒加载，控制前端内存占用
4. 原文采用「索引字节定位 + GitHub Range分片请求」加载
5. 繁简检索、权重排序、关键词高亮全部通过预构建静态数据实现
6. 整体架构无体积膨胀、无部署风险、无维护压力
