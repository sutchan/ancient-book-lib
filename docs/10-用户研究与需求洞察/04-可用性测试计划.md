# 可用性测试计划

> **说明**：本计划用于指导「古籍通 AncientBook」的可用性测试，验证产品是否满足目标用户需求，识别可用性问题。测试应在 v1.3.0 功能上线后执行，后续每季度或重大版本更新后重复执行。

---

## 一、测试目标

1. **验证核心闭环**：用户能否独立完成"搜索→找到书→阅读→划词溯源→下载"的完整流程
2. **识别可用性问题**：发现用户在使用过程中遇到的困惑、错误、效率低下的环节
3. **验证需求假设**：验证用户画像和需求优先级报告中的假设是否成立
4. **收集改进建议**：收集用户对功能、内容、体验的真实反馈和建议
5. **建立基线数据**：记录任务完成率、完成时间、满意度评分，作为后续版本对比的基线

---

## 二、测试范围

### 包含的功能/页面

| 模块 | 页面/功能 | 测试重点 |
|------|-----------|----------|
| 首页 | Hero 搜索框、十大馆藏、精选典籍、最近阅读 | 首次访问理解、搜索入口发现 |
| 搜索 | 全文检索、书目匹配、筛选 | 搜索结果相关性、繁简混合查询 |
| 书目浏览 | /catalog 馆藏筛选、子类筛选、分页 | 找书效率、筛选可用性 |
| 远程阅读 | /read/remote 加载、章节导航、繁简切换、字号调节、划词检索、下载 | 阅读体验、功能发现、大文件加载 |
| 精选书阅读 | /book/[id] 本地演示书 | 与远程阅读体验一致性 |
| 详情页 | /catalog/book 元数据、章节目录 | 信息完整性、目录加载 |

### 不包含的功能

- 人物考据页（/relation）——使用频率低，后续单独测试
- 生僻字查询（/character）——辅助功能
- 数据统计页（/stats）——运营向，非用户核心任务

## 三、测试用户招募

### 目标用户画像配比

| 画像 | 人数 | 招募渠道 | 筛选条件 |
|------|------|----------|----------|
| 文史研究者 | 3 | 高校文史院系微信群、学术论坛 | 近 3 个月内查阅过古籍，有论文写作需求 |
| 传统文化爱好者 | 3 | 小红书/豆瓣国学小组、朋友推荐 | 近 1 个月内阅读过古籍或国学相关内容 |
| 学生 | 2 | 高校学生群 | 文史相关专业或有通识课论文需求 |
| 开发者/数据使用者 | 2 | GitHub、技术社区 | 有 NLP/数据处理经验，对古籍数据感兴趣 |

**总计**：10 人（定性测试的合理样本量，能发现 80% 以上的可用性问题）

### 排除条件

- 参与过本项目开发或设计的人员
- 完全不了解古籍/传统文化的用户（非目标用户）
- 视力障碍或其他可能影响测试的身体条件（可单独进行无障碍测试）

## 四、测试任务设计

### 任务一：查找并阅读《论语》（核心任务）

**场景描述**：你想阅读《论语》的原文，请找到这本书并开始阅读。

**成功标准**：
- [ ] 用户在 2 分钟内找到《论语》
- [ ] 用户成功进入阅读页
- [ ] 用户能切换到简体对照
- [ ] 用户能调节字号

**观察要点**：
- 用户首先尝试在哪里搜索（首页搜索框 vs 精选典籍 vs 十大馆藏）
- 用户是否注意到繁简切换按钮
- 用户是否能找到字号调节控件

### 任务二：查找"天行健"的出处（研究者核心任务）

**场景描述**：你记得"天行健，君子以自强不息"这句话，想找到它在《周易》中的具体位置和上下文。

**成功标准**：
- [ ] 用户在搜索框输入"天行健"
- [ ] 用户在搜索结果中找到《周易》
- [ ] 用户进入阅读页并找到包含"天行健"的章节
- [ ] 用户能阅读上下文

**观察要点**：
- 用户是否知道可以用搜索功能
- 搜索结果是否包含《周易》
- 用户是否能在章节列表中找到"乾卦"
- 用户是否使用划词检索功能

### 任务三：划词溯源（差异化功能）

**场景描述**：在阅读《论语》时，你看到"学而时习之"这句话，想知道其他古籍中是否有类似表述。

**成功标准**：
- [ ] 用户选中"学而时习之"
- [ ] 用户注意到划词检索浮动按钮
- [ ] 用户点击按钮跳转到搜索结果页
- [ ] 用户能看到其他古籍中的匹配结果

**观察要点**：
- 用户是否知道可以划词检索（功能发现率）
- 浮动按钮位置是否合理
- 搜索结果是否满足预期

### 任务四：下载原文（研究者/开发者任务）

**场景描述**：你想下载《论语》的原文 TXT 文件，用于离线阅读或研究。

**成功标准**：
- [ ] 用户在阅读页找到下载按钮
- [ ] 用户看到合规下载提示
- [ ] 用户成功下载文件

**观察要点**：
- 用户是否注意到下载按钮
- 合规提示是否造成困扰
- 下载的文件是否能正常打开

### 任务五：大文件加载体验（边界场景）

**场景描述**：你想阅读《御定佩文韵府》（约 61MB 的大文件），请尝试加载并阅读。

**成功标准**：
- [ ] 用户在书目中找到《御定佩文韵府》
- [ ] 用户看到大文件警告提示
- [ ] 用户理解警告含义并做出选择（阅读/下载/返回）
- [ ] 如果选择阅读，能看到加载进度

**观察要点**：
- 大文件警告是否清晰易懂
- 用户是否理解 61MB 意味着什么
- 加载进度条是否缓解焦虑
- 用户是否会选择直接下载而非在线阅读

### 任务六：移动端阅读（爱好者场景）

**场景描述**：（使用手机）你在地铁上想用手机读 10 分钟《道德经》。

**成功标准**：
- [ ] 用户在手机上找到《道德经》
- [ ] 页面在手机上显示正常（无横向滚动、文字可读）
- [ ] 用户能翻页/切换章节
- [ ] 阅读进度自动保存

**观察要点**：
- 移动端加载速度
- 触控操作是否流畅
- 字号在手机上是否合适
- 是否有布局错乱

## 五、测试流程

### 测试前准备（10 分钟）

1. 欢迎用户，介绍测试目的（"测试产品好不好用，不是测试你"）
2. 说明测试流程和时间（约 45 分钟）
3. 签署知情同意书（录音/录像授权）
4. 填写用户背景问卷（年龄、职业、古籍阅读经验、技术能力）
5. 演示"出声思考法"（Think Aloud），让用户练习

### 测试执行（30 分钟）

1. 按顺序执行任务一至任务六（可根据用户画像调整任务顺序和数量）
2. 每个任务开始前朗读场景描述
3. 用户操作过程中保持沉默，仅在用户卡住超过 1 分钟时给予提示
4. 记录用户的操作路径、出错点、评论、情绪反应
5. 每个任务完成后询问："这个任务难不难？哪里让你困惑？"

### 测试后访谈（10 分钟）

1. 整体满意度评分（1–10 分，SUS 量表简化版）
2. 最喜欢的功能是什么？
3. 最不满意的地方是什么？
4. 如果只能改进一个地方，你希望改进什么？
5. 你会向朋友推荐这个网站吗？为什么？
6. 还有什么想说的？

## 六、数据收集与分析

### 定量数据

| 指标 | 定义 | 目标 |
|------|------|------|
| 任务完成率 | 独立完成任务的用户比例 | ≥ 80% |
| 任务完成时间 | 从任务开始到完成的时间 | 任务一 ≤ 2 分钟，任务二 ≤ 3 分钟 |
| 出错次数 | 每个任务中用户操作错误的次数 | ≤ 2 次/任务 |
| 求助次数 | 用户主动询问或需要提示的次数 | ≤ 1 次/任务 |
| SUS 满意度评分 | 系统可用性量表（0–100） | ≥ 70 分（良好） |
| NPS 净推荐值 | "你有多大可能向朋友推荐？"（0–10） | ≥ 30 |

### 定性数据

- 用户操作路径记录（截图/录屏）
- 用户出声思考的原话引用
- 用户困惑点和错误点分类
- 用户改进建议汇总

### 问题严重程度分类

| 级别 | 定义 | 处理优先级 |
|------|------|------------|
| **严重** | 用户无法完成核心任务，或导致数据丢失/错误 | 立即修复，下一个版本必须解决 |
| **重要** | 用户能完成任务但效率低下，或频繁出错 | 下一版本修复 |
| **一般** | 用户体验不佳但不影响任务完成 | 排入后续版本 |
| **轻微** | 视觉/文案小问题 | 累积修复 |

## 七、测试产出物

1. **可用性测试报告**：包含测试概述、定量数据汇总、定性发现、问题清单（按严重程度排序）、改进建议
2. **问题跟踪表**：每个问题的描述、严重程度、涉及页面、复现步骤、建议修复方案、状态
3. **用户原声引用集**：有代表性的用户原话，用于说服团队和指导设计
4. **录屏/截图归档**：脱敏后的测试录屏和关键截图

## 九、注意事项

1. **避免引导性问题**：测试中不使用"你有没有看到搜索按钮？"这类引导性问题，改用"你现在想做什么？"
2. **不解释不辩护**：用户遇到问题时，不立即解释"这个功能其实是这样用的"，先观察用户如何自行解决
3. **保护用户隐私**：录屏/录音前必须获得明确授权，报告中不出现用户真实姓名
4. **小步快跑**：如果发现严重问题，可立即修复后重新测试该任务，不必等到全部测试完成
5. **持续测试**：本计划不是一次性的，每个重大版本更新后都应重复执行核心任务测试
